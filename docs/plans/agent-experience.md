## Decisions
1. New table `ticket_replies` (not `ticket_comments`): `reply_id INT AUTO_INCREMENT PK, company_id INT NOT NULL, ticket_id INT NOT NULL, author_id INT NULL, author_role VARCHAR(20) NOT NULL` (`'Customer'|'Agent'|'Admin'`, snapshot so history survives role/user changes), `author_name VARCHAR(150) NULL` (snapshot display name), `is_internal TINYINT(1) NOT NULL DEFAULT 0, body TEXT NOT NULL, created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP, INDEX idx_ticket_replies_ticket (company_id, ticket_id, created_at, reply_id)`. No FKs, same reasoning as tickets. Added in `ensureTicketRepliesTable(pool)` called from `initMySQLSchema` right after `ensureTicketsTable` (idempotent; warn-only). Body max 5000 chars (`REPLY_BODY_MAX`), min 1 after trim.
2. Visibility: `is_internal = 1` rows are agent/admin-only notes. Customer-facing queries ALWAYS filter `is_internal = 0` in SQL (model function `listPublicReplies`), never filter in JS; the customer DTO has no `isInternal` field. Staff queries return both with `isInternal`.
3. Who can reply: assigned Support Agent (public or internal), customer (own ticket, public only), company admin (public or internal, optional but included: small marginal cost, same service function). Admin may reply on any ticket of their company; agent only on tickets where `assigned_agent_id = agent` AND `company_id = agent company`.
4. Closed tickets: nobody posts to a `Closed` ticket (409 `TICKET_CLOSED`). `Resolved` tickets: agents/admins may still post (e.g. final note); a customer reply on a `Resolved` ticket reopens it (status -> `Open`, `resolved_at` NULL) in the same operation; documented behaviour, simplest customer flow, no separate reopen endpoint. Customer reply on `Open`/`In Progress` leaves status alone. Agent public reply on an `Open` ticket does NOT auto-change status (explicit status control only; avoids surprising state changes). Reopen runs through `ticketModel.updateTicket(companyId, id, {status:"Open"})`.
5. Agent status updates: agents may set `In Progress`, `Resolved`, `Closed`? Decision: agents may set `Open`, `In Progress`, `Resolved` only. `Closed` stays admin-only (final state, also blocks replies). Agents cannot change priority or assignee (admin owns triage). Transition from `Closed` by an agent -> 409 `TICKET_CLOSED`.
6. Ticket created but unassigned after an agent is deactivated: agent no longer assigned, so agent endpoints 404 (indistinguishable from missing). Reassignment while an agent has the detail open: next request 404 -> UI shows not-found state.
7. Concurrency: reply insert is guarded by re-validating the ticket within the same service call (find ticket scoped by company+agent, then insert). A small race (reassignment between check and insert) is accepted; mitigate with a conditional insert in SQL: `INSERT INTO ticket_replies (...) SELECT ?,?,?,?,?,?,? FROM tickets WHERE company_id=? AND ticket_id=? AND status <> 'Closed' [AND assigned_agent_id=?] LIMIT 1` and treat `affectedRows = 0` as 409/404 re-check. Keep it: one statement closes the closed/assignment race.
8. No attachments, no editing/deleting replies, no email notifications, no AI draft replies in this item (item 7 settings only; AI is out of scope). Pagination of replies: return all, hard cap `LIMIT 500` oldest-first (document).
9. Reply rate guard: per-author cap (e.g. 30 replies per rolling minute is overkill); use a simple per-ticket cap `MAX_REPLIES_PER_TICKET = 500` -> 409 `REPLY_LIMIT_REACHED`. Counted in the model (`countReplies(companyId, ticketId)`).
